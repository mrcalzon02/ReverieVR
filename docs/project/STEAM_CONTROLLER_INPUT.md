# Original Steam Controller (2015) — Android input investigation

**Status:** Android HID inspection utility committed; not yet connected to UI or validated on handset. The original controller's full native reports have not been decoded in ReverieVR.

## Reference hardware evidence (Galaxy S9, user observations, 2026-10-10)
- Bluetooth pairing accepted with original Steam Controller.
- Android displayed “Configure physical keyboard”.
- In Firefox the right trackpad moved the system pointer.
- Trigger input acted as a mouse click; clicking the right trackpad did not register the click in that test.
- These facts do **not** establish complete gamepad/dual-trackpad/gyro/paddle support.

## Upstream protocol resources
- Linux GPL-2.0+ hid-steam driver: https://github.com/torvalds/linux/blob/master/drivers/hid/hid-steam.c — documents 2015 controller mouse/keyboard “lizard mode” and raw HID support. **Reference only**; do not copy GPL-licensed source into the application without licensing review.
- Original Steam Controller driver and documented event layout: https://github.com/cvuchener/steamcontroller-linux-kernel — stick, left/right pads, trigger axes, grips, gyro and accelerometer.
- SDL-derived original-controller Android work (marked untested): https://github.com/MrCloudy2/moonlight-android-steam-controller — compatibility research, not verified support.
- https://github.com/SonicDX12/SteamController-Android is specific to **2026 Ibex**; explicitly excludes the original 2015 controller. Do not use its report layout for this device.

## Implemented source
`app/src/main/java/io/github/mrcalzon02/reverievr/input/HidInputInspector.java`: non-invasive Android `InputDevice` enumeration and button/motion reports; read-only and designed to avoid logging text typed on physical keyboards.

## Integration steps
1. Connect inspector to an explicit developer diagnostic panel and lifecycle-safe device-added/removed/rescan controls; do not log every frame or persist events by default.
2. Hook key/motion dispatch (without consuming ordinary Android events) and display controller-specific event reports with device ID and source.
3. For observed lizard-mode controls, preserve normal Android mouse behavior and record supported buttons/axes. Do not infer trackpad click semantics from visual layout.
4. Only if needed, add optional original-controller vendor HID/BLE GATT report backend with pairing, permissions and report validation, plus transition back to safe default mode on detach/error.
5. Normalize complete physical inputs into module profiles; explicitly handle double input if default HID mouse and raw reports coexist. Keep essential shell recovery outside remappings.
6. Validate S9 pairing/reconnect, independent pads, touch/contact state, triggers, paddles, thumbstick, menu/face keys, gyro, battery if available, and haptics separately. No receiver is required for the observed Bluetooth pairing.

## Acceptance
Not complete until built, diagnostic events shown on a real S9, and behavior verified across the application, DOS host and native modules. No placeholder UI toggle or claims of raw driver access before actual support.

The inspected handoff contains 22 parts / 11,882 triangles; seven parts retain reported topology flags. Original ZIP/CAD are preserved separately. The user requested a Google Drive package for the online instance to perform programming/hookup. Renderer/controller integration, exact Android report mappings and device/performance acceptance remain planned. The rendering approximation must not be represented as unchanged manufacturing CAD or as an independently authored substitute.

## Bonded Bluetooth Battery Service probe — Android 10 (2026-10-11)

On the actual Galaxy S9 API 29 firmware, Android's API 31+ InputDevice battery interface is absent. When the original Steam Controller is explicitly selected and already enumerated by Android HID, the shell now activates a read-only asynchronous probe against an already **bonded** BLE controller's standard Battery Service (0x180F)/Battery Level characteristic (0x2A19). This does not scan, request Location, open any USB device, or send proprietary mode commands. A successful 1-byte 0–100 GATT reading populates the controller battery slot and is refreshed every two minutes while selected. Missing service, unavailable permissions, detach, failed read, timeout and controller switch leave the battery as **unknown**. No guessed voltage-to-percentage map is used. The original controller's BLE firmware may not expose 0x2A19; until independently tested on S9 this remains a conditional capability and proper native Valve battery/status packet support remains outstanding. A pure Java GATT decoder regression test covers invalid and boundary levels.

## Galaxy S9 observed original-controller alias repair — 2026-10-11

User-supplied Android 10 / One UI 2.5 Bluetooth screenshot lists the paired, reportedly actively used 2015 original controller as **`SteamController`** (one word). Prior `SteamControllerIdentity.matchesAndroidHid` recognized only `Steam Controller` and `Valve Steam Controller` and therefore rejected the actual advertised name. The single authoritative matcher now recognizes explicit bounded original-controller aliases, including `SteamController`, and is used by Android HID device detection, the active selector, virtual controller mouse source matching and the bonded-BLE battery probe. Regression cases verify the no-space alias with unknown VID 0 and Valve VID 0x28de, and reject other vendors, `Steam Deck`, generic `Steam` and 2026 controller labels.

**Do not conflate paired with connected:** Samsung's paired-device list does not alone prove Android has enumerated a live HID input device. `Enter VR` still requires a live, nonvirtual Android InputDevice reporting mouse, keyboard or gamepad sources, or an explicitly ready Daydream provider. If the new APK continues to display disconnected during actual controller input, collect an `HidInputInspector.enumerate()` diagnostic and associated actual HID event IDs / device sources on the S9, without assuming the Bluetooth friendly name equals Android's InputDevice name. No Location permission checks or USB receiver. The reported screenshot is real hardware identity evidence, not an end-to-end HID acceptance test.

## scrcpy UHID for VR entry and live input (2026-10-11)

Accept a scrcpy-named, enumerated Android UHID keyboard, mouse or gamepad as a valid VR source, while generic keyboard/mouse devices remain insufficient. Explicit active-controller choice now includes scrcpy HID, with automatic mode accepting it when a higher-priority Daydream, Steam or normal gamepad source is not active. Scrcpy input is routed into the existing shell pointer/select path and normal hosted HID inputs, rather than adding a second renderer or backend. Stage A input test reports scrcpy keyboard/motion events without capturing typed characters. No requirement for Bluetooth, Location, USB receiver, or special permissions from ReverieVR. Scrcpy's default Android SDK event-injection mode does not create detectable UHID devices; run scrcpy with `--keyboard=uhid`, `--mouse=uhid`, or `--gamepad=uhid` as appropriate. UHID availability and device labels need to be checked on the reference Android 10 Galaxy S9; this commit and automated builds do not prove headset/hardware operation.

## scrcpy UHID Xbox-compatible gamepad identity correction (2026-10-11)

The first scrcpy UHID source slice recognized named `scrcpy` keyboard/mouse devices, but it failed explicit scrcpy gamepad-only selection. Upstream scrcpy `app/src/uhid/gamepad_uhid.c` declares `SC_GAMEPAD_UHID_VENDOR_ID=0x045e`, `SC_GAMEPAD_UHID_PRODUCT_ID=0x028e`, and `SC_GAMEPAD_UHID_NAME="Microsoft X-Box 360 Pad"`; unlike its keyboard/mouse inputs, this gamepad does **not** advertise a scrcpy name. Source: https://github.com/Genymobile/scrcpy/blob/master/app/src/uhid/gamepad_uhid.c . `ScrcpyHidIdentity.matchesCompatibleGamepad` therefore adds that exact triple as an **explicit scrcpy-selection fallback only**, with an Android gamepad/joystick source requirement. The companion Stage A selector displays *scrcpy / Xbox-compatible HID (available)*, not a verified scrcpy origin. On Android 10, scrcpy gamepad UHID and a genuine Xbox 360 controller with that same VID/PID/name cannot be distinguished through public `InputDevice` metadata, so **Automatic** mode retains generic gamepad behavior and does not assert scrcpy provenance. Explicit scrcpy selection accepts its gamepad events (previously blocked as an unrelated gamepad), and the VR renderer can use gamepad virtual-pointer aim. No Bluetooth scan, Location check, USB hub, or new integration dependency is introduced. JVM tests cover the exact upstream signature and negative cases. Galaxy S9 input-device capture and live headset tests are still required; CI APK compilation is not a device test.

## Galaxy S9 scrcpy visual heading, digital twin and HUD regression (2026-10-11)

The startup home view was premultiplying the world-to-eye raw headset view by NEGATIVE shell yaw, doubling its angular offset instead of cancelling it. Apply POSITIVE shell heading instead. Normal shell panels already use the corrected view, so their extra offset yaw is removed; headset-following Quick Menu retains current relative yaw. The phone-panel UI hit ray likewise must not apply the shell yaw twice. No Cardboard IPD, stereo eye viewport or projection changes.

Under scrcpy UHID the virtual Daydream controller model applied +yaw about Y to a local -Z forward while the interactive ray was pointing +sin(yaw) X, effectively a reversed visible orientation. Model rotation now uses -rayYaw and ray generation is centralized in VirtualControllerAim, with -65..65 degree and upward-pitch regression tests. Physical tracked Daydream quaternion routing remains unchanged.

The vendored untextured Daydream OBJ button caps can exhibit strange triangular highlights due to differently oriented per-vertex normals. The renderer now disables the normal vertex array for button caps and supplies one fixed normal (0,1,0), while body and touchpad retain imported normals. No shader rewrites or external textures are required. The phone/controller battery labels move to the upper arc area (x350 y77/103 instead of x326 y188/216), and the HUD UV crop AND matching clip-quad vertices extend to y42 (previously y67); downward reveal and bar geometry remain unchanged. These source and JVM-test fixes still require real Galaxy S9 visual acceptance.

## Persistent keyboard in Home and corrected headset startup (2026-10-11)

After the Galaxy S9 screenshot confirmed the home dais was still a featureless gray slab, the renderer now allocates and uploads a dedicated persistent keyboard texture on that existing dais geometry in Home mode. It uses the live VrKeyboardEditor and 51 existing key rectangles, with ray/UV hit testing, hover feedback, and key presses that edit the text; the COPY + CLOSE key commits without leaving Home. The old separate keyboard mode remains supported. The desk keyboard can be visible while the projected phone panel is active, with input remaining reserved for the phone panel until dismissed. Keyboard bitmap, GLES texture and dirty state are independently owned and cleaned up on renderer shutdown. JVM key/UV tests cover first and last keyboard buttons, commit button, and no-hit rays.

The related earlier fix now derives the startup/recenter heading from raw Cardboard head-view instead of a potentially opposite headset-forward vector. The power HUD is shrunk by 70 percent, anchored at the upper-right eye, and has centered, smaller text. These are code-level repairs, not physical Galaxy S9 acceptance evidence.

## Home keyboard input ownership when projected phone panel is active (2026-10-11)

Post-commit review found a real control blocker: the Home renderer draws the desk keyboard even with its phone-screen panel visible, but the Home hit-test previously returned **only** `hitPhonePanelControls(...)` in that state. A visible desk keyboard could never receive input. Both states now share the same `hitHomeKeyboard` ray/UV test; when the phone panel is active, the shell takes the nearest valid hit between its separate vertical control panel and the horizontal physical desk keyboard. The existing Home menu buttons remain suppressed with the phone panel shown. Keyboard visibility, typing, and COPY + CLOSE are no longer conditional on disabling the phone panel. Added key hit-test regressions for desk center, commit key, edge miss, and behind-camera rays. Source-level fix; physical headset acceptance pending.

## scrcpy UHID keyboard text reaches Home desk editor (2026-10-12)

Code review after phone-test #111 identified a second keyboard-path gap: Android accepted scrcpy UHID keyboard events, but in Home they were consumed by `StandardHidInputRouter` and forwarded to `VirtualInputBus` rather than the visible `VrKeyboardEditor`. A narrow `VrActivity.routeScrcpyHomeKeyboardInput` now directs active scrcpy-labelled HID **keyboard** KeyEvents into a bounded 64-command queue handled on Cardboard's GL thread. It supports Unicode printable characters, Backspace/Delete, cursor Left/Right, Tab and Enter using the same caret/buffer as controller-clicked keys; both texture views are dirtied after edits. Only Home and the dedicated Keyboard screen (outside the orientation/quick menu) accept the path. DOS/native guest input, other controllers, Ctrl/Alt shortcuts and the separate input-selection paths are left intact. Repeated key down is supported; release events are consumed without double typing. JVM tests cover mixed pointer+HID editing, accented Unicode, non-BMP characters, control edits, invalid commands, and the 2048-character cap. Device acceptance still requires S9/scrcpy physical testing. No Location, USB dongle or new Android permissions.
